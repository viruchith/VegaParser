# Orientation evaluation

This page records how well VegaParser's output supports the question a developer asks an LLM: *"What is this repo, where is X, and what do I need to read to change Y?"*

The evaluation is **offline and deterministic**. It makes no LLM calls and no network requests. Re-run it with:

```powershell
.venv\Scripts\python scripts\evaluate_orientation.py            # print results
.venv\Scripts\python scripts\evaluate_orientation.py --write-docs  # refresh the block below
```

## What it measures

**Extraction.** Precision and recall of four categories against hand-written ground truth in `evaluation/ground_truth.json`:

- `files`: parseable files discovered and parsed.
- `symbols`: classes, functions and methods, keyed as `path::Name` or `path::Class.method`. Dunder methods and Java constructors are excluded.
- `dependencies`: internal file-to-file import edges.
- `urls`: external `http(s)`/`ws(s)`/`ftp` URLs.

**Retrieval.** For each question in `evaluation/questions.json`, the strategy proposes a context pack. Scored on file level:

- `recall`: expected files in the pack ÷ expected files.
- `precision`: expected files in the pack ÷ files in the pack.
- `hit rate`: share of questions where at least one expected file is in the pack.
- `pack source chars`: total source characters of the files in the pack. This is a size proxy, not a token count.

Strategies:

- `full_bundle`: every parsed file. This is what `bundle` includes today, with no selection.
- `keyword`: files ranked by overlap between question terms and path, symbol names and docstrings, capped at k. It is a simple baseline, not a tuned competitor.

## Corpus

Three hand-written repositories under `tests/eval_corpus/`, 31 files in total. The ground truth was written from the source files, not from tool output, so the scores can't be tuned to the tool.

| Repo | Files | Language notes |
|---|---:|---|
| `python_app` | 11 | Packages, dataclasses, `urllib` call with a URL constant, pytest test |
| `typescript_app` | 10 | Relative ES imports, classes, interfaces, `fetch` with URL constant, Jest-style test |
| `java_app` | 10 | Maven-style package layout, classes, Spring annotation, URL constant |

The 19 questions cover entry points, business logic, external calls, configuration, models and tests.

## Known limits

- The corpus is small and synthetic. The numbers are a regression baseline for these fixtures, not a claim about any real repository.
- The retrieval scores are file-level. They don't measure whether the LLM answers correctly.
- Ground truth may contain errors. If a score looks wrong, check the ground truth first.

## Baseline findings

These findings were measured on the code before workstreams 2–5. Status is noted for each.

1. **Dependency recall is 0%.** *Open, workstream 4.* The CLI calls `ParserEngine.infer_internal_dependencies`, which only matches bare file stems. Dotted Python imports (`app.models`) and relative JS/TS imports (`./server`) never resolve. The richer resolver in `repo_parser/parser/dependencies.py` is imported but never called. Every import-based ranking depends on fixing this.
2. **Java URLs were never extracted.** *Fixed in workstream 2.* `ParserEngine.parse_file` returned early for `java`, `sql` and `plsql` without running endpoint enrichment. Those files now get the same endpoint extraction and redaction as other languages. URL recall for this corpus went from 66.7% to 100%.
3. **TypeScript interfaces are not extracted as symbols.** `AppConfig` and `Item` are missed.
4. **Full-bundle retrieval has recall but no precision.** Every question gets every file, so precision is a fraction of the file count. This is the problem the budgeted bundle must solve.
5. **Keyword retrieval misses questions whose answer shares no words with the question.** "Where does the application start?" returns nothing for both `python_app` (`main`) and `java_app` (`App.main`), because neither file contains the word "start" or "application".
